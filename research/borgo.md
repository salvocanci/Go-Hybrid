## What it actually is (verified from README + source)

Borgo is a Rust-syntax, ML-flavored language that **transpiles to readable Go source** and
is designed to be "fully compatible with existing Go packages" (README). Its stated goal,
verbatim: "I want a language for writing applications that is more expressive than Go but
less complex than Rust. Go is simple and straightforward, but I often wish it offered more
type safety. Rust is very nice to work with (at least for single threaded code) but it's too
broad and complex, sometimes painfully so."

The feature set it adds on top of Go:

- Algebraic data types (enums with payloads) + pattern matching with exhaustiveness checking
- `Option<T>` instead of nil and `Result<T, E>` instead of multiple return values
- The `?` operator for error propagation (like Rust / Swift)
- Immutability by default with `mut` annotations (variables AND struct fields)
- Closures/lambdas, `if`/`match` as expressions, tuple types, struct-update spread syntax
- `newtype`s transparent over their underlying type (e.g. `2 * time.Second` type-checks)
- Direct Go-idiom concurrency: `spawn f(x)` → `go f(x)`, `defer`, channels (`Channel<T>`),
  `select`, `for x in receiver` ranges — all mapping 1:1 to Go primitives
- `@rawgo(...)` escape hatch for verbatim Go code inside Borgo (used by the stdlib for
  things like `Unwrap` and zero-values)
- Imports Go stdlib packages via generated `.brg` binding files: "import packages from Go
  stdlib" in every README example (`use fmt`, `use net.http`, ...)

Compiler pipeline (single `cargo run -- build` command): compile all `.brg` files in the
current folder → emit `.go` files → the user then runs `go run .` themselves (README's own
two-step instructions: "The compiler will generate .go files, which you can run as normal").
There is no bundling of the Go compiler (suggested in open issue #42, never acted on).

The standard library is ~50 `.brg` files under `std/` (fmt, os, net.http, sync, time,
crypto, ...). They are *binding* files: functions declared with `EXT` bodies ("external",
i.e. implemented by real Go at link time) plus small Borgo-level conveniences implemented
in-language (e.g. `Option.IsSome`) or via `@rawgo`. Bindings for the Go stdlib were
generated by the separate Go importer (below); `std/modules.json` maps paths to module names.

## What Hybrid should extract (specific techniques for our Go/Rust interop language)

1. **The comma-ok/Result bridge**: mapping `Result<T, E>` to native Go `(T, error)` and
   `Option<T>` to `(T, bool)` at function-signature boundaries, while materializing tagged
   structs only in expression contexts, gives Go-idiomatic APIs with ML-level internal type
   safety. This dual-representation trick is Borgo's single best idea — adopt it for every
   Hybrid→Go call boundary.
2. **Enum-as-tagged-struct encoding**: `type XTag int` + iota + flattened payload fields +
   `make_X_Cons()` constructors. Zero runtime magic, debuggable, generics-compatible,
   stable across Go versions. Our FFI IDL enums (which rust2go lacks!) should use exactly
   this representation — it is representable from BOTH Rust (`#[repr(C)]` with a discriminant)
   and Go, so it doubles as the cross-language enum ABI.
3. **Pattern-match compilation to plain ifs** with a `_matches` state variable: dumb,
   correct, portable. (We can improve verbosity with early-exit switches, but the semantics
   — evaluate patterns left-to-right, first match wins — are what we should keep.)
4. **Roc's exhaustiveness checker (UPL-1.0)**: Borgo lifted `compiler/src/exhaustive.rs`
   (Maranget 2007) from Roc in 694 lines. We should do the same — it's the same algorithm
   Rust uses, permissively licensed, and battle-tested.
5. **The Go-side importer**: a small Go program using `go/ast` that generates language
   bindings for arbitrary Go packages, with the `(T,error)`→Result / `(T,bool)`→Option
   conventions, method→impl conversion, a REWRITE_MODULES path normalizer, and a DENY_LIST
   falling back to `any`. This is the exact mechanism for Hybrid's "call any Go crate"
   promise; Borgo proves it works for the entire Go stdlib.
6. **Boundary-native signatures**: emitting Go-native signatures where Go code will call,
   language-native types inside — keep APIs familiar to Go teams. This is our "Go teams
   adopt incrementally" requirement in codegen form.
7. **`@rawgo` escape hatch**: every source-to-source language needs verbatim target-code
   escape hatches; Borgo's stdlib itself needs it (Unwrap, zeroValue). Hybrid should have
   `@rawgo`/`@rawrust` equivalents, clearly marked and linted.
8. **Markdown-driven end-to-end snapshot tests**: `.md` files containing code + expected
   output, a deno runner invoking the compiler via a JSON protocol, expect-test snapshots,
   plus an examples runner that executes emitted Go. Cheap, reviewable, and catches
   codegen regressions that unit tests miss.
9. **Hand-rolled lexer/parser + HM inference in ~6k lines, zero deps**: proof that a
   usable type checker (unification, occurs check, bidirectional hints, generics) is a
   months-scale solo project — scope reassurance for Hybrid's own frontend.
10. **FS abstraction for the compiler** (`fs.rs`: LocalFS/WasmFS): one-line cost that
    enables a browser playground (wasm-bindgen build shipping std bindings to the client).
    A playground was Borgo's best marketing artifact — do the same.

## Failure modes / lessons (why momentum died)

- **No license = adoption killer**. The single most-repeated complaint in the tracker
  (#41, #43, plus #11 referenced from it): people who wanted to try or fork Borgo could
  not, legally. "Without a license, forking is not an option" (jcszymansk, #43). Lesson
  for us: dual MIT/Apache-2.0 from commit zero (we already have this), and never let the
  repo exist without it.
- **No releases, no distribution**: zero git tags; open unanswered issues asking for
  prebuilt binaries (#30), cargo/brew packages (#27), `generate binary` (#19). Users had
  to `cargo build` a compiler from a moving-target repo. Lesson: ship versioned artifacts
  and an installer path early, even if the compiler is rough.
- **Bus factor = 1**: 167/168 commits by one person; after his attention left (late 2023),
  nothing happened — not even issue triage. Lesson: recruit a second committer before
  launch, and keep the codebase small enough (Borgo's ~12.5k lines was plausible for
  handover) that someone COULD take over — but with no license, nobody legally could.
- **Two-toolchain developer experience**: `cargo run -- build` then `go run .` — Borgo
  never integrated the Go build (issue #42 "Consider bundling and wrapping a Go compiler"
  went unanswered). The "one build command" experience Hybrid promises is precisely the
  gap that made Borgo feel like a curiosity rather than a tool. Lesson: own the whole
  build, or at least `go` invocation, inside our driver.
- **Transpiling caps the language**: everything must be expressible as readable Go — no
  move semantics, no ownership (#44 asked about ownership+goroutines; unanswered), no
  borrow checking, and `mut` is only a lint. The value proposition ("better type system")
  stops at the frontier of what Go's runtime model can express. Hybrid's approach (real
  Rust for the safety-critical parts) is strictly stronger; Borgo is the ceiling proof of
  "Go with better types" — popular idea (4.6k stars from a standing start), execution
  unable to go further without changing the substrate.
- **Generated-code quality issues leaked**: still-open bugs like #29 ("generates code with
  invalid generics when calling helper functions") and #28 ("capture in the lambda causes
  stack overflow") in core codegen paths since May 2024, plus #33 (playground's own
  examples fail to compile). Lesson: snapshot-test the hell out of codegen; our
  correctness bar must be higher than Borgo's before we market anything.
- **No LSP / tooling** (#31 open, unanswered): syntax without editor support loses the
  "Go teams adopt it" audience. Lesson: plan `gopls`-style LSP or VS Code extension early.
- **The graveyard has occupants**: Soppo (halcyonnouveau/soppo), Dingo (MadAppGang/dingo),
  gala (martianoff/gala), Lisette — same idea, same Rust→Go-syntax space, all small.
  Prior art confirms the niche is attractive but none has broken out; differentiation
  must come from the Rust-interop angle (which none of them do), not from syntax alone.

## Licensing (license, compatibility with dual MIT/Apache-2.0)

- The repository has **NO license at all** — all rights reserved by default. GitHub API
  confirms `license: null`; issue #41 (2025-01) asks for one and is unanswered.
- Practical effect: legally, nobody may copy, modify, or redistribute Borgo's code without
  the author's permission; even the 4.6k-star audience was advised not to use it (#41:
  "it is impossible for many potential users" to try it; #43: "without a license, forking
  is not an option").
- One exception inside the tree: `compiler/src/exhaustive.rs` is taken from the Roc
  compiler under **UPL-1.0** (permissive, Apache-2.0-compatible) with attribution intact.
- Compatibility with our dual MIT/Apache-2.0:
  - we may NOT copy Borgo's own compiler code into Go-Hybrid (unlicensed) — treat every
    file except `exhaustive.rs` as reference-only
  - the *ideas and mappings* in this note (tagged-struct enums, Result↔(T,error) bridge,
    match compilation strategy) are unprotectable facts/techniques and safe to implement
    independently
  - if we want the exhaustiveness algorithm, take it from Roc directly (UPL-1.0, like
    Borgo did) — NOT from Borgo's copy
  - our repo's dual MIT/Apache-2.0 is unaffected as long as we don't vendor their code

## Verdict for Go-Hybrid (one paragraph)

**Study intensely, reimplement independently, take exactly one file's worth of code from Roc instead.** Borgo is the closest prior art to Hybrid's "better type system over the Go ecosystem" promise and its repository is a complete, readable blueprint of that architecture — hand-written lexer/parser, Hindley-Milner inference, Roc-derived exhaustiveness checking, tagged-struct enum lowering, the Result↔`(T, error)` boundary bridge, a go/ast-based binding importer covering the whole Go stdlib, wasm playground, and end-to-end markdown snapshot tests — built by one person in eight months (proof of scope) and then abandoned (proof of every non-technical failure mode we must avoid: no license, no releases, no bus factor, no integrated build, no tooling). For Go-Hybrid the plan is clear: adopt its *mapping tables and test methodology* as our Go-codegen baseline, source the exhaustiveness checker from Roc under UPL-1.0, and differentiate on exactly the axis Borgo could not cross — real Rust interop with a single build command — while copying its license-and-release discipline lessons in the opposite direction.
